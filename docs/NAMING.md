# docs/ 文件命名规则

规定 `docs/` 目录下所有文件的命名与序号分配规则，适用于三类对象：顶层文档、`acceptance-reports/`（分阶段验收报告）、`screenshots/`（入库截图）。本文与 `AGENTS.md` 的相关条目同源，修改任一处时同步另一处。

## 1. 顶层文档

- **命名**：中文名 + `.md`，直接说明文档职责，不带序号前缀。现有：`产品理念.md`、`开发计划.md`、`调研报告.md`。
- **例外**：本文件用英文惯例名 `NAMING.md`。
- **边界**：顶层只放长期维护的项目级文档。逐阶段的验收记录一律进 `acceptance-reports/`，不在顶层新增「验收报告」类单文件。
- **子目录**：`acceptance-reports/`、`screenshots/`，规则见下。

## 2. acceptance-reports/（分阶段验收报告）

- **文件格式**：`序号-中文阶段简介.md`，如 `1-仓库与工程环境.md`。
- **序号分配**：按验收完成的先后顺序从 1 起逐步 +1；不跳号、不复用旧号、不按时间插队重排。当前已用 **1–13**（与里程碑的对应见该目录 `README.md` 索引页）；下一份新报告从 **14** 开始。
- **简介取词**：取阶段章节标题，去掉 `M0 ·` / `附加 ·` / `修复轮 ·` 前缀；可精简但不得改变含义；不含空格与 Windows 文件名非法字符（如 `：`、`/`、`「」`）。原章节标题在文件内保留为首行 H1 原文（如 `# M0 · 仓库与工程环境`）。
- **一个分支一份文件**：`feat/*` / `fix/*` 分支验收完成后单独新建一份（见 `AGENTS.md` §4）；同一分支内的多轮改动（首轮实现 + 后续修复、视觉微调等）**并入该分支已有的那份**，按「第一轮 / 第二轮 …」小节追加，**不新建文件、不另占序号**。只有新分支才新建报告文件，序号在分支首次建立时分配一次。
  - 适用范围：`feat/*`、`fix/*` 等功能 / 修复分支。`main` 上的里程碑报告仍按里程碑一份一份。
  - 历史例外：11、12 两份报告同属 `fix/home-live-ux` 分支，是本规则生效前的产物，**不合并且保持原样**；规则自 13 号报告起生效。
  - 截图号段跟随报告文件序号（见 §3），同一分支的后续轮次共用该号段。
- **README.md**：索引页（总说明 + 文件索引 + 里程碑完成度表），不参与序号编号。

## 3. screenshots/（入库截图）

- **文件格式**：`序号-小写英文短描述.png`，描述用 `-` 连接单词，如 `100-zhuri-home.png`。
- **序号分配（按报告号分段）**：`序号 = 所属验收报告文件序号 × 10 + 报告内次序（0–9）`。
  - 例：报告 `11-首页与跑步体验7项修复.md` 的第 3 张截图为 `112-xxx.png`。
  - 单份报告截图超过 10 张时，先与维护者确认扩段方式再新增，避免侵占其他报告的号段。
  - 未绑定具体报告的展示类截图（如 README 界面图）归入其引入阶段对应的报告号段。

## 4. 改名与维护

- 改名一律用 `git mv` 保留历史；改名后全局更新引用（至少检查 `README.md`、`AGENTS.md`、`docs/开发计划.md` 与各验收报告索引）。
- 新增阶段文件或截图前，先查该目录 `README.md` 索引与本文的重命名记录，确认已用序号，再按规则递增分配。
