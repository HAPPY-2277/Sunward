### 本轮发现的既有缺陷（第 1、2 项已修，其余等用户决定）

| # | 缺陷 | 现场 |
|---|---|---|
| 1 | ✅ **本轮已修**（提交 `fix: 恢复未完成的跑步时带回原开始时间`）：恢复后的记录 `startTimeMs=0` —— `RunSession.restore()` 只设 `simulated`，不设 `startWallClockMs`，`persist()` 于是写出 `startTimeMs = 0`：记录页显示「1月1日 00:00」，而报告按开始时间归属周期，这条记录会被算到 1970 年 | 修法比原先设想的更准：`InProgressStore.Snapshot` 新增 `startWallClockMs` 字段（前台服务每 5 秒写快照时一并存），恢复时优先用它；旧快照没有这一项时退回 `savedAtMs − elapsedMs`（`Snapshot.resolvedStartWallClockMs`）。**没有**采用「恢复时刻 − 已跑时长」：快照 12 小时内都算新鲜，隔天再恢复就会把记录算到新的一天。改 5 个源文件 + 5 个新单测，模拟器实测记录显示 `10月26日 17:15` |
| 2 | ✅ **本轮已修**（提交 `fix: 恢复后继续跑不再丢掉已跑距离`）：恢复后已跑距离被第一个新点覆盖归零 —— `RunTracker.restore()` 确实设了 `this.distanceM = distanceM`，但下一个点被采纳时执行 `distanceM = filter.acceptedDistanceM`，而新 tracker 的过滤器是从 0 开始累加的 → 崩溃前跑的距离直接丢掉。实测：中断前 0.14 KM，恢复后通知立刻变 0.01 KM，最终记录只剩恢复后跑的距离（时长不受影响，`accumulatedMs` 与过滤器无关）。`restore()` 原 KDoc 只声明「历史轨迹与分段无法还原」，没说距离会丢，属于实现与意图不一致 | 修法：`RunTracker` 新增 `distanceOffsetM` 基线 —— `restore()` 存下已跑距离、`onPoint` 改写 `distanceM = distanceOffsetM + filter.acceptedDistanceM`、`start()` 与跨数据源防御 `resetSeriesForNewSource()` 都清零（换源等于「重新记一段」，恢复出来的基线不再适用）；KDoc 补明「距离通过基线接着算，历史轨迹与分段仍无法还原」。分段锚点用的本来就是恢复后的距离，改完自然对齐。补 2 个单测；模拟器实测 0.16 KM → 强杀 → 恢复 → 0.16 KM → 15 秒后 0.21 KM，连续累加 |
| 3 | **`pm clear` 后用 adb 模拟入口会崩**：`ensureRunning()` 的权限判断是 `!tracker.hasPermission() && !wantSimulated`，模拟模式跳过权限检查，但 `location` 类型前台服务不论真假轨迹都要求定位权限 → `SecurityException: Starting FGS with type location … requires … ACCESS_FINE_LOCATION` | `ui/LiveRunActivity.kt` `ensureRunning()` ← `service/RunForegroundService.kt:105` `promoteToForeground`。真实用户走权限弹窗不会触发，只影响 adb 调试；临时绕过 `adb shell pm grant com.runclub.android android.permission.ACCESS_FINE_LOCATION`（README 已写明） |
| 4 | 字符串 `gps_disabled` / `perm_denied` / `restore_discarded` 从未被引用；定位服务未开启时 `locationFlow()` 直接 close，界面没有任何提示 | `res/values/strings.xml` |
| 5 | `Text.Label` / `Text.WeeklyLabel` / `Text.WeeklyUnit` 仍是 9sp，`Text.Eyebrow` / `Text.WeeklyFooter` 10sp，与 AGENTS.md「全站字号下限 11sp」不一致（M8 遗留） | `res/values/themes.xml` |
