## 5. 技术架构与关键决策

### 5.1 分层与包结构

```
com.runclub.android
├── ui/                      表现层：Activity + 自定义 View + Adapter
│   ├── HomeActivity         运动首页（activity.html）
│   ├── LiveRunActivity      实时跑步（live-run.html）
│   ├── ResultActivity       成绩页（run-result.html）
│   ├── RecordsActivity      记录页：历史/报告双 Tab（records.html）
│   └── widget/              TrackView、PaceChartView、WeekBarView 等自绘控件
├── service/
│   └── RunForegroundService 前台服务（location 类型）+ 常驻通知
├── tracking/                领域层：与 Android 框架解耦的纯逻辑
│   ├── RunStateMachine      IDLE/RUNNING/PAUSED/FINISHED 状态机
│   ├── LocationTracker      LocationManager 封装 + 回调
│   ├── TrackPointFilter     精度/速度/时序过滤链（去漂移）
│   └── RunMetrics           Haversine 距离、配速、卡路里、分段
├── data/
│   ├── local/RunDatabase    SQLiteOpenHelper + DAO
│   ├── model/               RunRecord、TrackPoint
│   └── repo/RunRepository   单一数据出入口
├── report/
│   └── ReportBuilder        周/月/年聚合（同一套代码，不同时间窗）
└── util/                    TimeFormatter、PaceFormatter、DateRange 等
```

**设计原则**：`tracking/` 与 `report/` 是**纯 Kotlin，不依赖 Android 框架**（除 Location 数据类型），因此可以在 JVM 上直接跑单元测试——这是 §5.7 测试策略的基础。

### 5.2 关键技术决策表

| 决策点 | 选择 | 理由（含调研报告依据） |
|---|---|---|
| **定位源** | **系统 `LocationManager` + `GPS_PROVIDER`**（`NETWORK_PROVIDER` 兜底），**不用** `FusedLocationProviderClient` | FLPC 依赖 Google Play 服务，**国内多数手机没有 GMS，会直接失败**；`LocationManager` 是 AOSP 系统服务，无此依赖。与调研报告 §6.4 结论一致（`geolocator` 插件也是"FLPC 优先、无 GMS 回退 LocationManager"） |
| 定位参数 | `minTime = 1000ms`、`minDistance = 0f`（demo 阶段不做距离过滤，交由软件层过滤） | 1Hz 是行业主流（Strava/Garmin 同量级）；省电优化留到后续 |
| **前台服务类型** | `android:foregroundServiceType="location"` | Android 14+ 强制声明类型；⚠️ **绝不用 `dataSync`**——Android 15 起 `dataSync`/`mediaProcessing` 每 24h 最多跑 6 小时即被系统停止，而 `location` 类型不受此限（调研报告 §6.4 已核实） |
| 服务基类 | `androidx.lifecycle.LifecycleService` | 便于观察生命周期与协程作用域管理 |
| 后台权限 | **只申请"仅使用期间"定位权限**（`ACCESS_FINE_LOCATION`），**不申请** `ACCESS_BACKGROUND_LOCATION` | 前台服务运行期间视为"使用中"，足以完成锁屏记录；避开"始终允许"的两步授权流程与用户流失（调研报告 §6.4 的建议设计）。⚠️ 若实测发现某机型锁屏后断轨，我**会先问你**再决定是否加"始终允许" |
| UI 技术 | **XML 布局 + View**（不用 Jetpack Compose） | AGP 9 / Kotlin 2.4 与 Compose 编译器的版本匹配是额外风险点；原型是固定布局，XML 足够，且自绘轨迹本来就要写自定义 View |
| 主题 | 单一深色主题，色值取自原型 | 见 §5.3 设计令牌 |
| 持久化 | **SQLite（`SQLiteOpenHelper`）**，不用 Room | Room 需引入 KSP 插件，而 KSP 与 Kotlin 2.4.21 的版本对应关系本次未能确证（Maven 上 `symbol-processing-api` 版本序列为 2.3.x，存在错配风险）。demo 数据模型只有两张表，手写 SQLite 更稳、零额外插件。**若你坚持要 Room，请告知，我改为 Room 并先验证 KSP 版本** |
| 图表 | 自定义 View 用 `Canvas` 手绘 | 零依赖；原型用 ECharts，Android 端引入 ECharts 需 WebView（性能与离线都差），MPAndroidChart 虽已复活但增加依赖面 |
| 异步 | Kotlin 协程 + `Flow` | 定位回调 → Flow → UI 收集，天然背压与取消 |
| 架构模式 | 轻量 MVVM（`ViewModel` + `StateFlow`），不引入 Hilt/Dagger | demo 规模不需要 DI 框架 |

### 5.4 数据模型（SQLite 两张表）

```sql
CREATE TABLE run (
  id            INTEGER PRIMARY KEY AUTOINCREMENT,
  start_time    INTEGER NOT NULL,      -- epoch millis（UTC）
  end_time      INTEGER NOT NULL,
  timezone      TEXT    NOT NULL,      -- 如 Asia/Shanghai，报告按此界定"本周/本月"
  duration_ms   INTEGER NOT NULL,      -- 净运动时长（不含暂停）
  distance_m    REAL    NOT NULL,
  avg_pace_s    REAL,                  -- 秒/公里
  calories      REAL,
  status        TEXT    NOT NULL,      -- COMPLETED / DISCARDED
  note          TEXT
);

CREATE TABLE track_point (
  id         INTEGER PRIMARY KEY AUTOINCREMENT,
  run_id     INTEGER NOT NULL REFERENCES run(id) ON DELETE CASCADE,
  seq        INTEGER NOT NULL,
  time_ms    INTEGER NOT NULL,
  lat        REAL    NOT NULL,         -- WGS-84（存储铁律，见下）
  lon        REAL    NOT NULL,
  accuracy_m REAL,
  altitude_m REAL,
  speed_mps  REAL,
  paused     INTEGER NOT NULL DEFAULT 0
);
CREATE INDEX idx_tp_run ON track_point(run_id, seq);
```

> **存储铁律**：轨迹点一律存 **WGS-84 原始坐标**。将来接高德（GCJ-02）时只在渲染层转换，导出 GPX 给 Strava/Garmin 才不会整体偏移（调研报告 §7.3）。

**派生指标不入库**：每公里分段、心率区间、周/月/年统计都由 `ReportBuilder` 从原始点重算，避免"删掉一条记录后总统计不同步"这类 bug（调研报告 §5.5 中咕咚被吐槽的真实问题）。

### 5.5 核心算法（与调研报告 §6.2/§6.3 一致）

| 项 | 实现 |
|---|---|
| 距离 | Haversine 逐点累加，R = 6,371,008.8 m |
| 去漂移过滤链 | ① 丢弃 `accuracy > 30m` ② 丢弃速度 > 12 m/s（约 43 km/h）③ 丢弃时间戳非递增 ④ 位置差分速度与 `Location.speed` 偏差过大时剔除 |
| 速度平滑 | EMA，`α = 0.4`（`s_t = α·x_t + (1−α)·s_{t−1}`） |
| 当前配速 | 平滑速度取倒数并限幅在 `2'30"`–`15'00"`/km；无有效速度时显示 `--'--"` |
| 平均配速 | `净用时秒 / 距离公里`，格式 `m'ss"` |
| 每公里分段 | 按**累计距离**触发（不是按时间） |
| 卡路里 | `kcal = 距离(km) × 体重(kg) × 1.036`（跑步常用近似式）；**体重默认值待你确认，见附录 C 问题 2** |
| 计时 | 用 `SystemClock.elapsedRealtime()` 累计，**不用 `System.currentTimeMillis()`**（避免用户改系统时间或时区导致时长错乱）；暂停时停止累计 |
| 轨迹绘制 | 墨卡托近似投影（demo 范围内平面投影足够）→ 计算包围盒 → 等比缩放并居中，四周留 24dp 边距 → 先画白色描边（宽 13px）再画荧光绿/橙色主线（宽 8px）→ 起点/终点/当前位置标记 |

### 5.6 报告页聚合逻辑（M7）

- 单一入口 `ReportBuilder.build(period: WEEK | MONTH | YEAR, refDate, tz)`，三个周期共用一套代码，只是时间窗不同（调研报告 §8.1 原则 5）。
- 周：ISO 周（周一为起点）；月：自然月；年：自然年。**全部按 `run.timezone` 界定**，跨月跑步按**开始时间**归属。
- 输出：总里程、次数、总时长、平均配速、环比变化、目标完成度、按日/按月的里程柱状数组 + 配速折线数组、一句洞察文案（规则模板生成，不用 AI）。
- 图表：`PaceChartView` 复刻原型的双轴效果——左轴里程柱状（荧光绿、圆角），右轴反向配速折线（橙色、平滑、圆点），配速轴 `inverse = true`（配速越小越高）。

## 附录 A · 高德 Key 申请指引（你要求的教学部分）

> 拿到 Key 之后，我可以在 **M8**（本次 demo 之外）把自绘轨迹替换成真实高德地图底图 + 轨迹纠偏。

**前置条件**：需要一个手机号 + 支付宝/实名认证（个人开发者即可，免费）。

**步骤**

1. 打开 <https://lbs.amap.com/> → 右上「注册」→ 完成个人开发者注册与实名认证。
2. 进入「控制台」→「应用管理」→「我的应用」→ **创建新应用**
   - 应用名：`RUN CLUB`（随意）
   - 应用类型：选「出行」或「其他」
3. 在该应用下点「**添加 Key**」，填写：
   - Key 名称：`runclub-android-debug`
   - 服务平台：**Android 平台**（⚠️ 不要选 Web 端 / JS API，那是网页用的）
   - **发布版本号**：可留空
   - **Package Name（包名）**：`com.runclub.android` ← 必须与本工程一致
   - **SHA1**：填 **debug 签名的 SHA1**（见下方获取方法）
4. 提交后得到一串 32 位 Key，复制给我。

**获取 debug 签名 SHA1（我在 M1 之后可以直接帮你算，你也可自己执行）**

```powershell
# 方式一：从 APK 里读（M1 产出 APK 后可用）
& "$env:JAVA_HOME\bin\keytool.exe" -printcert -jarfile D:\a\android\app\build\outputs\apk\debug\app-debug.apk

# 方式二：从 debug keystore 读
& "$env:JAVA_HOME\bin\keytool.exe" -list -v -keystore "$env:USERPROFILE\.android\debug.keystore" -alias androiddebugkey -storepass android
```

输出里的 `SHA1: XX:XX:...` 就是要填的值。

**⚠️ 三个必踩的坑（提前告诉你）**

1. **包名 + SHA1 必须与构建时完全一致**，否则地图白屏、定位返回错误码 `INVALID_USER_SCODE`。所以：**先让我构建出 APK，再拿 APK 的 SHA1 去申请 Key**，顺序不能反。
2. **高德 SDK 8.1.0 起强制隐私合规接口**：必须在使用任何功能前调用
   `MapsInitializer.updatePrivacyShow(context, true, true)` 与 `updatePrivacyAgree(context, true)`，
   `AMapLocationClient.updatePrivacyShow/Agree` 同理——**否则地图白屏、定位无数据**（这是我在线核实过的高德官方要求）。App 里需要先有隐私政策弹窗，用户同意后才调用 `updatePrivacyAgree`。
3. **坐标系**：高德返回的是 **GCJ-02**，我们库里存的是 **WGS-84**。接高德时我会用官方 `CoordinateConverter` 做转换，**只在渲染层转，不改存储**。

**替代方案（不想申请 Key 时）**：继续用自绘轨迹；或后续接 MapLibre + 自建瓦片（免 Key 但需瓦片源）。
